# 16 — HNSW: the recall-versus-speed curve

Everything before this page treated the vector index as exact. It is not. An
approximate nearest-neighbour index trades recall for speed, and the whole
vector-database half of this project is only worth building if that trade can
be measured rather than assumed.

Tables regenerated by `python -m scripts.bench all`; current output in
[`docs/experiments/bench-ann.md`](experiments/bench-ann.md).

## Why synthetic vectors

The plan called for 1k / 10k / 100k **random** vectors of dim 384 instead of
embedding 100k real chunks. Embedding 100k chunks on a laptop CPU is hours of
MiniLM, and it would measure MiniLM. Random unit vectors exercise exactly the
code path under test, in seconds.

They are also wrong in a specific, useful direction. Random Gaussian vectors in
384 dimensions are nearly equidistant from each other — the curse of
dimensionality in its purest form, no cluster structure for a proximity graph
to exploit. Real embeddings cluster hard. So every recall number below is a
**pessimistic bound**, and the last table shows by how much.

One detail that would have silently invalidated all of this: Qdrant does not
build an HNSW index until a segment crosses `indexing_threshold` (20MB by
default) and brute-forces below it. At 1k points the default would have made
"ANN latency" mean "exact latency". Every benchmark collection sets
`indexing_threshold=1` and waits for `indexed_vectors_count` before timing
anything.

## Scale

| points | build s | pts/s | http ms | p50 ms | p95 ms | exact p50 ms | speedup | disk MB | server RSS MB |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1,000 | 0.7 | 1,424 | 1.17 | 1.68 | 3.25 | 1.46 | 0.9x | 4.9 | 140 |
| 10,000 | 4.7 | 2,106 | 1.18 | 2.09 | 3.21 | 1.78 | 0.9x | 49.8 | 155 |
| 100,000 | 72.4 | 1,382 | 1.17 | 2.52 | 4.41 | 5.21 | 2.1x | 242.6 | 158 |

The `http ms` column exists because without it this table tells a lie. A
do-nothing REST call to Qdrant costs 1.17ms. That is the floor under every
other number here, and it is *most* of them.

Read the p50 column net of that floor: 0.5ms at 1k, 0.9ms at 10k, 1.35ms at
100k. Search cost grows roughly logarithmically, which is what HNSW promises.
Brute force net of the floor goes 0.3 → 0.6 → 4.0ms, which is linear, which is
what brute force promises.

**At 1k and 10k points, exact search is faster than ANN.** The graph traversal
costs more than scanning 10,000 vectors. Only at 100k does ANN win, and it wins
2x. The OpsSense index is 85 points and httpx is 1,465 — both are firmly in the
region where `--exact` is the better setting, and the ANN machinery in this
project earns nothing on the corpora it was built for. Saying so is the point
of measuring.

Build throughput is flat at 1.4-2.1k points/s, so indexing is linear: 100k
points is 72 seconds, and a million would be about 12 minutes.

## ef_search: the knob you can turn at query time

10k points, m=16, ef_construct=100, recall@10 against Qdrant's exact search.

| ef_search | recall@10 | p50 ms | p95 ms |
| --- | --- | --- | --- |
| 4 | 0.114 | 1.51 | 1.91 |
| 8 | 0.114 | 1.50 | 1.87 |
| 16 | 0.182 | 1.55 | 2.09 |
| 32 | 0.294 | 1.60 | 2.08 |
| 64 | 0.460 | 1.73 | 2.32 |
| 128 | 0.662 | 1.91 | 2.49 |
| 256 | 0.872 | 2.20 | 2.70 |
| 512 | 0.974 | 2.49 | 3.21 |

This is the curve. Recall climbs from 0.11 to 0.97 while p50 goes from 1.5ms to
2.5ms — and 1.17ms of both is HTTP, so the real search cost went 0.34ms →
1.32ms, roughly 4x, for 8.5x the recall. `ef_search` is the only one of the
three knobs that needs no rebuild, which makes it the one to tune first and the
one to expose to callers.

The shape matters more than the values: it is concave. Every doubling of
`ef_search` buys less recall than the last, and past 256 you are paying real
latency for the final few percent. If a product can tolerate 0.87 recall, 256
is free relative to 512.

## m: graph degree, fixed at build time

10k points, ef_construct=100, queried at ef_search=64.

| m | build s | recall@10 (ef=64) | p50 ms | disk MB |
| --- | --- | --- | --- | --- |
| 4 | 2.3 | 0.116 | 1.89 | 48.8 |
| 8 | 3.2 | 0.234 | 1.82 | 49.1 |
| 16 | 4.3 | 0.462 | 2.15 | 49.8 |
| 32 | 4.3 | 0.694 | 2.09 | 50.8 |
| 64 | 3.3 | 0.788 | 2.62 | 51.6 |

`m` is how many neighbours each node keeps. Too few and the graph is
disconnected enough that greedy search gets stranded in a local minimum — 0.116
recall at m=4 is exactly that. Going 4 → 64 costs 2.8MB of disk (6%) and buys
6.8x the recall at the same query budget.

Disk barely moves because the graph is small next to the vectors it indexes —
16x more neighbours per node changed the collection by under 6%. Anyone tuning
`m` downward to save space is optimizing the wrong term.

## ef_construct: how hard the builder looks

10k points, m=16, queried at ef_search=64.

| ef_construct | build s | recall@10 (ef=64) | p50 ms |
| --- | --- | --- | --- |
| 16 | 2.2 | 0.294 | 1.79 |
| 32 | 2.3 | 0.418 | 2.21 |
| 64 | 4.3 | 0.418 | 2.21 |
| 128 | 6.3 | 0.460 | 1.94 |
| 256 | 5.3 | 0.478 | 1.90 |
| 512 | 6.3 | 0.500 | 2.00 |

Diminishing returns arrive fast and early. 16 → 128 nearly triples build time
for +0.17 recall. Past 128 recall gains +0.04 in total, and build time stops
responding at all — 256 built faster than 128 here, which is measurement noise
at this scale and a fair warning not to read three significant figures into
these columns. Query latency is unaffected throughout, as it should be:
`ef_construct` shapes the graph, it does not appear at query time.

Compared side by side at ef_search=64: `m` moved recall 0.12 → 0.79, while
`ef_construct` moved it 0.29 → 0.50. **`m` is the stronger build-time knob**,
and it is the one to spend on.

## Real embeddings: how pessimistic is the synthetic bound?

The same ef_search sweep over 1,415 real httpx function embeddings, with 50
held-out corpus vectors as queries.

| ef_search | recall@10 (real) | p50 ms |
| --- | --- | --- |
| 4 | **1.000** | 1.46 |
| 8 | 1.000 | 1.55 |
| 16 | 1.000 | 1.63 |
| 512 | 1.000 | 1.45 |

Perfect recall at `ef_search=4`, where random vectors managed 0.114.

That gap is the entire lesson of this page. HNSW's published recall numbers
assume data with structure, and embeddings have enormous structure: MiniLM maps
code into a space where a function's neighbours are genuinely, locally near it,
so a greedy graph walk cannot get lost. Random vectors have no such structure,
so the walk is close to a random one.

Two honest caveats. This index is 1,415 points, small enough that recall would
be high for almost any parameter choice, so it demonstrates the *direction* of
the gap rather than its size at scale. And the queries are held-out corpus
vectors, which are in-distribution by construction — a real user's question
embedding sits further from any chunk than a chunk does.

**Practical reading: tune `ef_search` against your own data or you will tune it
against the wrong curve.** The synthetic sweep says you need ef=512; the real
data says ef=4 is plenty. Both are correct about their own inputs.

## Scalar quantization

100k points, m=16, ef_construct=100, `int8` with `quantile=0.99` and
`always_ram=true`.

| vectors | build s | recall@10 (ef=64) | p50 ms | p95 ms | disk MB | server RSS MB |
| --- | --- | --- | --- | --- | --- | --- |
| float32 | 81.5 | 0.084 | 2.29 | 5.30 | 242.6 | 160 |
| int8 scalar | 56.2 | 0.086 | 2.23 | 2.77 | 279.8 | 209 |

Quantization maps each float32 component onto one byte, so the textbook result
is 4x less memory for a small recall loss. That is not what happened, and the
reason is worth more than the expected result would have been.

**Disk went up by 37MB and RSS went up by 49MB.** 100k × 384 bytes is exactly
36.9MB: the quantized copy is an *addition*, not a replacement. Qdrant keeps
the original float32 vectors — it needs them to rescore, and they are
memory-mapped rather than resident, so they were never counted in RSS in the
first place. `always_ram=true` then pins the int8 copy into RAM on purpose.

So on this configuration quantization bought nothing, because the memory it
saves was already not being spent. It pays when the original vectors *are*
resident and you set them `on_disk`, or at a scale where the float32 vectors
cannot be mmapped comfortably. At 100k × 384 on a laptop, neither holds.

The one real win is in the tail: **p95 dropped from 5.30ms to 2.77ms.** Integer
distance computation is more predictable than float, and predictability is what
p95 measures. Recall was unchanged within noise (0.084 vs 0.086).

Both recall figures are low because this is 100k random vectors at
`ef_search=64` — compare the 10k row's 0.460. Recall degrades with corpus size
at fixed `ef_search`, which is the last thing worth taking from this page:
**ANN parameters are not portable across corpus sizes.** A setting tuned at 10k
is silently worse at 100k, and nothing in the system will tell you.

## Alternatives considered

- **Embedding 100k real chunks.** Hours of CPU to measure the embedding model
  instead of the index. The `real` sweep gets the same insight from 1.4k real
  vectors at 20 seconds' cost.
- **Measuring recall against a synthetic ground truth computed in numpy.**
  Qdrant's `exact=True` runs on the same server, through the same API, over the
  same stored vectors, so it also catches a storage or distance-metric mistake
  that an external ground truth would hide.
- **Binary quantization.** 32x compression and the biggest speedup, but it
  needs oversampling plus rescoring to stay usable, which is a second mechanism
  to explain. Scalar quantization was the one the plan asked for.
- **`docker stats` for memory.** Measures the container, including the page
  cache. Qdrant's own `memory_resident_bytes` from `/metrics` is what the
  process thinks it is using, which is the number to compare across configs.
- **Tuning `m` and `ef_construct` at 100k.** Each value is a full rebuild at 72
  seconds plus indexing. The shape of the curve is the deliverable, and 10k
  shows the shape for a twentieth of the wall clock.
